In this tutorial you will turn an informal claim into a structured argument. You will learn the
jPipe syntax, preview your model as a diagram in the IDE, and (optionally) reproduce the same result
from the command line.

# Objectives

By the end of this guide you will be able to:
- Create a justification model in the `.jd` format.
- Understand the relationship between **evidence**, **strategies**, and **conclusions**.
- Preview and export your model as a diagram.
- Peek "under the hood" with the diagnostic mode.

This tutorial only requires the [jPipe IDE](/tutorials/install/ide/). The command-line steps are
optional and assume the [compiler CLI](/tutorials/install/compiler/).
{: .notice--info}

# The scenario: is our release ready?

Imagine you are about to ship **version 2.0** of your product. Everyone *says* it's ready — but
"ready" is vague. jPipe lets you make that claim explicit and back it with evidence.

Let's make the implicit explicit:

- **The goal (conclusion):** *"Version 2.0 is ready to ship."*
- **The reasoning (strategy):** *"All release gates pass."*
- **The facts (evidence):** *"The test suite passes"* and *"The changelog is up to date."*

These three roles come from the [Toulmin model of argumentation](https://en.wikipedia.org/wiki/Stephen_Toulmin#The_Toulmin_model)
and a simplified [Goal Structuring Notation](https://scsc.uk/gsn) (GSN):

- **Conclusion** — the claim you want to establish.
- **Strategy** — the *warrant* linking the facts to the claim.
- **Evidence** — the *grounds*: concrete facts that support the strategy.

# Step 1 — Write the model

Create a file named `release.jd` (in the IDE, or your favourite editor) and enter:

```jpipe
justification release {
  // The claim we want to establish
  conclusion c is "Version 2.0 is ready to ship"

  // The reasoning that connects evidence to the conclusion
  strategy s is "All release gates pass"
  s supports c

  // The supporting evidence (grounds)
  evidence e1 is "The test suite passes"
  e1 supports s

  evidence e2 is "The changelog is up to date"
  e2 supports s
}
```

Every element is declared as `<keyword> <id> is "<label>"`, and support edges (`x supports y`) wire
the argument together: evidence supports a strategy, and a strategy supports the conclusion.

# Step 2 — Preview the diagram

In the IDE, open `release.jd` and run **jPipe: Open Diagram Preview** from the Command Palette
(`Ctrl+Shift+P` / `⇧⌘P`). The preview updates as you type.

# Step 3 — The same thing from the command line (optional)

If you installed the [compiler CLI](/tutorials/install/compiler/), you can export the model without
the IDE:

```
$ jpipe process -i release.jd -m release -f SVG -o release.svg
```

Breaking that down:

- `process` — compile and export a model (this is the default command).
- `-i release.jd` — the input source file.
- `-m release` — the name of the model to export.
- `-f SVG` — the output format (also `PNG`, `PDF`, `JSON`, `DOT`, …).
- `-o release.svg` — where to write it.

# Step 4 — Look under the hood with diagnostics

As models grow, it helps to see exactly how the compiler understood your code. The `diagnostic`
command reports problems and traces what it built — without exporting anything:

```
$ jpipe diagnostic -i release.jd
```

For our model it prints:

```
=== Diagnostics ===
(none)

=== Action Statistics ===
commands: 8 total (0 macro)
deferrals: 0

=== Model Summary ===
justification "release"
  elements:  conclusion(1), strategy(1), evidence(2)

=== Symbol Table ===
justification "release"  [release.jd:1:14]
  c   2:13
  s   4:11
  e1  7:11
  e2  9:11

=== Executed Actions ===
  1. create_justification('release').
  2. create_conclusion('release', 'c', 'Version 2.0 is ready to ship').
  3. create_strategy('release', 's', 'All release gates pass').
  4. support('release', 'c', 's').
  5. create_evidence('release', 'e1', 'The test suite passes').
  6. support('release', 's', 'e1').
  7. create_evidence('release', 'e2', 'The changelog is up to date').
  8. support('release', 's', 'e2').
```

What each section tells you:

- **Diagnostics** — warnings and errors. `(none)` means the model is syntactically sound and
  correctly connected.
- **Model Summary** — a quick audit: one conclusion, one strategy, two pieces of evidence.
- **Symbol Table** — where each identifier (`c`, `s`, `e1`, `e2`) is defined, handy for debugging
  larger files.
- **Executed Actions** — the step-by-step commands the compiler ran to build the model.

# Where to next?

Your first justification is intentionally shallow — a strategy asserting "all gates pass" with two
flat pieces of evidence. Real arguments have structure and, eventually, teeth:

- **[Language features](/tutorials/language/)** — grow the argument with **sub-conclusions** and
  split it across files.
- **[Make it executable](/tutorials/runner/)** — bind each piece of evidence to a real check with the
  jPipe Runner.

For fully worked, real-world justifications (including machine-learning quality arguments), browse
the [jpipe-examples](https://github.com/jpipe-mcscert/jpipe-examples) repository and the
[Bellairs CSE](https://github.com/jpipe-mcscert/bellairs-cse) material.
